Running the ARL

1 Overview
You can run your own copy of the ARL services for local development and testing. Each service is
provided both as a Docker image and as a Linux binary. The Docker images are the recommended way
to run them: one command starts a service together with everything it needs.
Every service needs an MQTT broker (Eclipse Mosquitto) and the ARL API, and the API needs a
PostgreSQL database. The provided compose file wires these up for you.

3 Running with Docker
3.1 The compose file
arl-test.​yaml is preconfigured to run every component. Run all commands from the arl-sim/​ folder.

An excerpt:
services:
api:
image: arl/api:0.1.0
depends_on: [postgres, mosquitto]
volumes: ["./config:/config:ro"]
ports: ["8080:8080"]
lwm:
image: arl/lwm:0.1.0
depends_on: [mosquitto, api]
volumes: ["./config:/config:ro", "./scenarios:/scenarios:ro"]
command: ["--scenario", "${ARL_SCENARIO:-}"]
environment:
ARL_SEED: ${ARL_SEED:-1}
ARL_SPEEDUP: ${ARL_SPEEDUP:-1}
ARL_START_TIME: ${ARL_START_TIME:-now}

Each service reads its configuration from config/​<service>.​toml. Edit that file to change a service’s
options (see its specification), then restart the service.

3.3 Common settings
These settings apply to every service and are given as environment variables in front of the command:
Variable

Default

Meaning

ARL_​SEED

1

Random seed. The same seed, start time, scenario and commands give
exactly the same data.

ARL_​SPEEDUP

1

Simulation speed relative to real time (e.g. 10 runs 10 simulated minutes
per real minute). Each service has a maximum (max_​speedup in its
configuration): RTA 50, MHE 2000, LWM, OPG and OWT 500.

ARL_​START_​TIME

now

Simulated start time: now or an RFC 3339 time, e.g. 2027-03-02T08:​00:​
00+02:​00.

ARL_​SCENARIO

none

Scenario file to load, as a path inside the container, e.g. /​scenarios/​
example.​toml (see Scenarios).

For example, to run the LWM ten times faster with a different seed:
ARL_SPEEDUP=10 ARL_SEED=7 docker compose -f arl-test.yaml up -d lwm

On Windows PowerShell, set the variables first: $env:​ARL_​SPEEDUP = "10", then run the command.
On Windows Git Bash, also put MSYS_​NO_​PATHCONV=1 in front of the command when a value is a path
(such as ARL_​SCENARIO=/​scenarios/​example.​toml); otherwise Git Bash rewrites the path and the
service cannot find the file.
Controls are enabled in your local copy. Commands must carry a researcher code that the ARL API
accepts for that service (see the ARL API specification).

4 Running the binaries
The binaries are static Linux x86_64 executables (on Windows, run them in WSL). They still need the
broker and the API, so start those with Docker first:
docker compose -f arl-test.yaml up -d api

Then run a service with its configuration file, pointing it at localhost:
MQTT_BROKER_ADDRESS=localhost ARL_API_ADDRESS=localhost ./bin/arl-lwm --config config/
lwm.toml

The RTA and LWM binaries need the site map and sky images, and the API binary its initial data. These
files are inside the Docker images; copy them out once (after docker load):

5 Scenarios
A scenario is a file of timed events that makes specific things happen: a thunderstorm, a heatwave, a
dish overheating, a pump failing. Marking runs and the live deployment use scenarios to create weather
and incidents, and you can use them to test that your platform handles every alert.
Every service reads the same scenario file and applies the events addressed to it. Load a scenario by
setting ARL_​SCENARIO when you start the services:
ARL_SCENARIO=/scenarios/example.toml docker compose -f arl-test.yaml up -d lwm rta

Put your own scenario files in the scenarios/​ folder; it is mounted at /​scenarios inside the containers.
Restart the services to load a changed file. Events are timed from the start time, so restarting replays the
scenario from the beginning.

A scenario is a TOML file with one [[event]] table per event:

3339 time

Key

Meaning

at

Required. +HH:​MM:​SS after the start time (hours may exceed 24), or an absolute RFC 3339 time.

service

Required. env for weather, or the service the event is for.

entity

The entity id (dish, site, room, crew member, plant entity), where the event needs one.

fault

Required. The event type.

duration

HH:​MM:​SS. Without it, a fault lasts until a repair event or the matching control fixes it.

params

Optional parameters of the event.

While a scenario event is active on an entity, the service’s own random faults on that entity are paused,
so the scenario controls what happens to it.

5.3 Service events
Each service specification lists its own events (section Scenario events). All services also accept repair
on an entity, which ends the faults on it. An example using every service is provided in scenarios/​
example.​toml.
